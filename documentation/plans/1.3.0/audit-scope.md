## Принципы распределения работы

- Полностью определённые массовые замены, оглавления, ссылки и перепечатка уже принятого правила — grade 0 / mechanical-worker.
- Небольшое изложение определённого правила и локальная реализация по готовому образцу — Low / impl-lite.
- Новый разбор формата, локальный алгоритм, тестовый инструмент и согласование нескольких потребителей — Mid / impl-medium.
- Сохранность пользовательской работы, передача владения работающим процессом, рискованная Git-операция — High / impl-hard только при соответствующей неопределённости/риске; не назначать High по числу файлов или потому, что тема называется «безопасность».
- impl-critical — только эскалация, не плановый исполнитель. Не использовать impl-ui для текста навыков Figma: это не реализация экрана приложения.
- Объединять связанные мелкие правки одного файла; разделять большие задачи с учётом чтения входа, реализации, проверки и исправлений. Цель — около 250 тысяч токенов или меньший бюджет при меньшем окне, с запасом, а не универсальный жёсткий предел.
- Ревью соразмерно: grade 0 — проверка оркестратора; Low — партии; Mid — один профильный проход; High — основное и независимое риск-ревью. Не понижать модели строгого ревью без сравнительных данных.

## Два обязательных сценария передачи между людьми

1. Один участник делает документы до архитектуры включительно и закрывает/отправляет их. Дизайнер забирает ветку и делает макеты. Первый участник делает ТЗ на экраны по макетам. Пользователь забирает всё на сверку документов и реализацию. На каждой передаче проверить состав коммита/отправки, подхват с клона, выбор этапов без закрепления за прежним участником и доступность отчёта разработки.
2. Один участник делает SRS, затем продолжает технические документы параллельно дизайнеру. Изменения объединяются, первый участник делает ТЗ на экраны, пользователь забирает всё на сверку и реализацию. Проверить независимые исходники при общих генерируемых файлах сайта, автоматическую пересборку при конфликте только сайта, остановку при реальном конфликте исходников и тот же свободный выбор этапа после pull/clone.

Это исходные сценарии пользователя. Дополнительно проверить передачу незавершённой разработки и восстановление после сжатия, но не подменять ими эти два сценария.
